anonymise.build_pack does dest.mkdir(parents=True, exist_ok=True) and never removes what is already there, so every re-evaluation of a run writes a fresh pack ON TOP of the previous one. Labels are assigned per bucket as NN.ext with NN unique within the bucket, so as soon as the file SET changes between passes the numbering shifts and the previous pass's files survive under labels the new manifest does not list. Measured 2026-08-23 across 68 submissions in 6 runs. Five runs are clean. wg-g4c-2026-08-21, evaluated nine times and straddling both the #69 cap removal and the #83 leak repair, carries 23 stale files in 222 - 10.4 percent - stack-correlated: unity 10, godot 8, ts 3, rust 2. Twelve are byte-identical to a live file so the judge sees the same code twice under two names; eleven carry content no manifest lists. Three consequences: the audit trail under-reports by ten percent; any cross-stack idiomatic or architecture ORDERING on this field is confounded by how much of each submission the judge was shown, which is finding 62's shape through a third mechanism that pack_completeness cannot see because it reads files_dropped_for_length and that is 0; and it silently defeats a repair, because the eleven unlisted files include the .codex hook scripts that #83 identified as the answer key - blinding survives only because neutralise reduces the leaking path to /WORKTREE at field.build_pack time, which is a second mechanism catching it rather than the repair working. The .src filename collisions this was first noticed through are a SYMPTOM: rebuilt from the manifests all 68 submissions collide 0 times, rebuilt from disk 15, and every colliding pair is one live file and one stale one. Reliability measurements are NOT affected because the pack is identical across repeats of one round; it is orderings that are confounded.
